# 验收：修改我的实例，不影响另一个实例

这次不需要安装 Minecraft。用小型合成内容观察真实文件复制，并验证重新准备不会覆盖个人修改。示例自动执行用户动作并检查结果，尚无图形界面。

## 先认清两类内容

```text
基础实例
    └── 玩家共享预设实例
            ├── 派生实例 A → 私有工作区 A + 用户 delta
            └── 派生实例 B → 私有工作区 B + 用户 delta
```

基础包、共享预设和 A/B 使用同一种实例修订。共享预设可以是汉化、性能配置或其他玩家整理的内容，它也可以直接准备自己的工作区。

用户 delta 则是运行后尚未发布的新增、修改、删除和类型变化。它留在各自工作区里，不自动改变预设，也不传给后代实例。当前没有“提升为新修订”按钮或导出功能。

## 一条命令走完用户故事

将本机 `JAVA_HOME` 指向 JDK 25，在仓库根目录运行：

```powershell
.\cleanroom\gradlew.bat -p cleanroom --no-daemon :workspace-nio:run
```

Linux/macOS 的命令入口为 `bash cleanroom/gradlew`，其余参数相同。缓存完整时可加 `--offline`，各平台是否已经验收见[记录](acceptance.md)。

按以下顺序读输出：

1. **我从预设派生 A、B。** 两个工作区初次收到相同内容，但文件是各自的私有副本。
2. **我改 A。** 修改一个配置、增加一个文件、删除一个原有文件。
3. **我重新打开并准备 A。** 服务从磁盘恢复基线，再读取实际文件；返回相应 delta，不重铺原配置、不复活删除文件、不清理新增文件。
4. **我检查 B 和原内容。** 它们没有受到 A 的修改影响。修改 B 也不能反过来改动 A。
5. **我从 A 的修订再派生 C。** C 继承 A 的已声明内容，不包含 A 工作区里尚未发布的个人改动。

示例出现断言失败时，进程返回失败，不能把前面某条成功输出当成整个故事通过。

## 保留文件，自己查看

使用保留模式运行一个新的实验：

```powershell
.\cleanroom\gradlew.bat -p cleanroom --no-daemon :workspace-nio:run --args="--keep"
```

实验目录位于 `cleanroom/workspace-nio/build/workspace-stories/` 下，具体位置由输出的相对路径确定。每次运行都创建新实验，不会重新准备上一个保留目录；该目录不进入 Git 提交。默认模式的临时样本在演示结束后清理。

打开本次实验目录，逐项核对：

- `A/config/game.cfg` 为 `A custom settings`，`B/config/game.cfg` 为 `B custom settings`。
- `artifacts/preset.cfg`、`preset/config/game.cfg`、`C/config/game.cfg` 仍为 `shared preset settings`。
- `A/my-notes.txt` 保留，B/C 中没有它；`A/mods/old.jar` 不存在，B/C 中仍存在。
- A 新建的 `user-empty/` 空目录仍在。

`.A.zpl-state/` 等同级目录是管理状态，不是需要复制进游戏的内容。不要编辑它们来模拟升级。不要把真实游戏目录搬进实验，也不要将含私人文件的实验目录打包公开分享。

## 为什么“再次准备”不会恢复出厂设置？

第一次准备保存一份不可变基线；后续比较这份基线和磁盘现状，识别你的改动。相同基线下，重新准备只检查并报告，不覆盖运行树。这也是删除文件不会重新出现的原因。

新修订或不同解析结果需要升级流程，当前入口会拒绝，而不是猜测哪些修改可以覆盖。首次准备中断或管理状态损坏时也不会宣布就绪；保留现场，自动恢复留给后续切片。

此次验收证明的是“私有工作区与修改保留”。游戏启动、共享存档、升级冲突解决和磁盘空间优化另行推进。详细行为见[文件系统规格](layerfs.md)，实现证据见[验收记录](acceptance.md)。
