## 使用三层证据，不相互替代

| 层次 | 输入与执行边界 | 能说明什么 |
| --- | --- | --- |
| 纯内核 | 内存树、固定组件元数据、模拟环境和端口；无网络、无真实账号 | 合并、约束、计划、冲突和状态规则可判定 |
| 适配器集成 | 临时目录、受控进程、测试服务、故障注入；路径由测试创建 | 真实文件操作、占用、取消、恢复及传输完成语义 |
| 产品 E2E | 固定游戏/包/Java 组合、真实桌面与账号；单独入口 | 该组合实际可安装、可交互、可启动并可安全收尾 |

默认测试不能扫描或修改开发者真实实例，也不自动执行旧 `src/test` 中硬编码路径的 `main` 流程。需要联网、游戏进程或账号的检查明确标记前置条件、数据位置和清理范围；账号凭据不进入测试报告。

核心的模拟 Linux/macOS 环境测试只证明规则求值，不证明对应平台能发行。临时目录里的复制测试也不证明 junction、符号链接或打包 native 已经正常工作。

## 文件与运行规则的最小覆盖

| 场景 | 主要证据 | 必须另外检查的边界 |
| --- | --- | --- |
| AR-01、AR-02；FS-01～FS-04、FS-14 | 纯解析及确定性夹具，至少 Windows/Linux/macOS 目标事实 | AR-02 的真实宿主替换在对应平台发行前补齐 |
| FS-05、FS-06、FS-08 | 三方差异夹具及临时目录运行修改 | 父层隔离、私有删除、提升范围、存档保留 |
| FS-07、FS-09～FS-13；AR-04、AR-07 | 真实临时文件系统、受控并发进程与提交阶段故障 | 链接能力缺失、外部变化、崩溃后占用及恢复 |
| RT-01～RT-07、RT-15 | 合成版本约束、环境、实例配置继承及无秘密计划夹具 | Java 8/17/21/25 的不同约束组合；父修订升级使配置和文件共同变更，不用合成规则冒充真实游戏支持矩阵 |
| RT-08～RT-11、RT-14；AR-06 | 受控进程、认证/传输替身、失败注入 | 创建与取消竞争、早退、native 未完成、秘密脱敏、会话占用 |
| AR-05、AR-08～AR-10 | 固定导入样本、自建实例、冲突制品及导出检查 | 未知本地 JAR、路径冲突、分发选择、不泄露秘密 |
| RT-12、RT-13；AR-03；UI-01～UI-06 | 真实桌面与选定游戏组合 | 启动器 Java 与游戏 Java 独立，实际输入、进度、退出和再次准备 |

使用小而有辨识力的夹具：基础实例→玩家共享预设实例→派生实例，另加私有工作区 delta；旧/新/个人配置三方冲突；只有本地 JAR 的自建实例；两个实例竞争共享存档；准备过程中止并恢复。每个故障场景须断言最终数据和状态，而不仅是“抛出了异常”。

## Qz 前端需要实际桌面证据

前期调研候选为 Core/Platform 的配套 `5.0.0-beta2`（2026-10-20 调研快照），实施时固定实际使用的版本和 native 产物。可从 [Qz Core](https://github.com/QuanhuZeYu/Qz-UILib-Core)、[Qz Platform](https://github.com/QuanhuZeYu/Qz-UILib-Platform)及其[桌面宿主规格](https://github.com/QuanhuZeYu/Qz-UILib-Platform/blob/5.0.0-beta2/specs/host/2026-10-11-uilib-desktop-spec.md)复查集成入口。前端选型已确定；下面验证其在本产品中的可用程度。

| 编号 | 操作 | 必须观察到的结果 |
| --- | --- | --- |
| UI-01 | 在实例名、搜索和路径选择相关文本输入中使用中文输入法，编辑、选择、粘贴中文 | 组合输入和提交可用，选区/光标正确；不能仅用 ASCII 或程序设置文本替代 |
| UI-02 | 在目标 Windows 设备改变缩放并移动/缩放窗口 | 文字与操作区可读可点，滚动、焦点和布局不丢失；记录实际 DPI/缩放组合 |
| UI-03 | 准备任务持续进展，切换页面，取消，再触发失败 | UI 不阻塞；最终状态不丢；错误和重试入口可理解，不留下旧页面订阅 |
| UI-04 | 浏览三层文件来源并处理升级冲突 | 能看到当前来源、个人修改和新候选；选择结果对应真实计划，不仅显示摘要计数 |
| UI-05 | 启动、游戏早退、关闭展示窗口、重新查看会话 | 进程状态与错误正确；关闭窗口不杀游戏或释放占用；日志有界且脱敏 |
| UI-06 | 从本机发行包启动，不借用开发环境 Java/classpath | 使用携带的 Java 25 与正确 native；选用另一个游戏 JVM 不改变启动器运行时 |

UI-01 的输入法组合体验是桌面适配的必要检查；如果库接口不能满足，应在 UI 宿主边界解决，不能把 Qz 类型或原生窗口逻辑塞进领域核心。平台支持和无障碍能力依据实际验收记录描述，不由跨平台库名推导。

## 按纵切面实施

### 0. 规格基线——已形成

独立分支保留本目录，完成文件语义、模块边界、运行时合同、验收方案和方法评估。检查链接、场景引用及跨文档冲突。此阶段不改变生产实现，也不安装规格工具。

### 1. 可测试的核心与安全工作区

建立最小构建和无 UI 入口，先实现纯层解析、实例修订及启动计划模型，再用临时工作区实现私有物化、三方差异和故障恢复。GTNH 与普通组件夹具共同参与；不等真实登录才检验核心。未通过写入隔离和恢复场景前，不接触用户真实实例。

构建工具须明确支持 Java 25；例如 Gradle 官方将运行于 Java 25 的支持起点列为 9.1.0，具体稳定版本和插件配套在建立构建时固定，不直接沿用旧 wrapper。[Gradle 兼容表](https://docs.gradle.org/current/userguide/compatibility.html)

### 2. 最小 Qz 桌面接入

显示真实实例投影、来源解释和任务进度，先完成 UI-01～UI-03 的设备检查，再扩充页面。使用相同应用用例接入测试前端和 Qz，防止演示界面另写一套安装/启动逻辑。此阶段可以与纯内核并行，只在端口和状态字段处协调。

### 3. 首个 GTNH 完整闭环

固定一个 GTNH 实包与组件修订：导入→派生个人实例→修改配置/加入本地模组→查看来源→准备→认证→启动→观察退出→重新准备。需证明父层未改、个人数据保留，Java 25 启动器确实使用独立的选定游戏 JVM。

RT-12 记录该具体组合，不将一次成功推广为所有 GTNH 版本。首次真实启动前，完成工作区占用交接和启动器退出/崩溃后的恢复机制；账户输入和应用身份按[入口待定项](README.md)落实。

### 4. 验证通用性与旧数据接续

完成普通非 GTNH 实例的 RT-13，使用适合该本地模组的加载器并确认模组确被加载，随后用受控旧格式副本证明导入、升级冲突、显式共享和导出。宣称“通用实例管理”前，两种实例均须走同一模型和用例；不要求二者使用同一加载器或 Java 版本。

旧样本迁移通过后才开放真实用户数据迁移入口。自动迁移默认关闭，预览和恢复来源先行；升级与迁移不能通过丢弃未知文件换取通过。

### 5. 扩展输入与发行平台

按需求补加载器、包格式、内容源及 Linux/macOS 宿主，每次复用现有契约并添加对应真实样本。跨平台发行需要各平台独立打包和本机验证；Java 的打包工具也按目标平台使用。[Java 25 jpackage 概览](https://docs.oracle.com/en/java/javase/25/jpackage/packaging-overview.html)

## 一项场景何时算通过

实施时记录：场景编号、测试入口或操作步骤、对应代码候选、输入/制品版本、OS/架构/Java、实际结果及剩余限制。故障恢复附恢复后的数据与状态；视觉交互附实际设备检查结果。

自动化证据可直接留在测试和 CI 结果中，手工结论随对应变更记录，不要求复制一份长期漂移的测试报告。跳过、未运行和失败不能标为通过；变更影响原输入或契约时重验，未受影响的有效证据可以复用。

当前纯内核和同基线私有工作区的证据见本页前两轮记录；升级、完整恢复与游戏运行继续按后续阶段验收。各阶段的负责人是承担该切片的实现负责人，整体取舍与交付验收由项目负责人负责；缺少的外部输入按[待定项](README.md)在对应动作前补齐。
