# 采用轻量规格驱动，暂不引入框架

评估日期：2026-10-21。

本项目需要规格驱动，主要用来固定文件继承、写入隔离、运行时兼容和失败恢复的契约。当前采用仓内 Markdown、稳定验收编号和 Git diff 即可；不安装 Spec Kit、OpenSpec，也不生成第二套 `specs` 权威目录。

## 为什么值得使用 SDD

旧 README、实际实现和用户希望保留的理念存在差异。重新实现时，如果只给代理“照旧代码重构”，缺陷和耦合也会被保留；如果只给愿景，又容易在覆盖顺序、可写共享和版本约束上各自解释。

规格用于明确输入、结果、不变量和失败路径；测试与运行证据验证这些约定。它不能替代试运行，也不能证明 AI 生成代码天然正确。只写当前切片所需的细节，不等所有加载器和平台都设计完才开始实现。

## 方法与工具的取舍

| 选项 | 能带来的帮助 | 本项目当前取舍 |
| --- | --- | --- |
| 仓内轻量 SDD | 正文契约、场景、设计理由与测试保持在同一变更里 | 采用；先验证流程是否足够，不引入额外运行环境 |
| GitHub Spec Kit | 提供可组合流程、模板与工作流，支持规格到计划和实现的过程 | 暂缓；现阶段单仓和少量契约不需要整套工具装配 |
| OpenSpec | 分开维护当前规格与变更提案，以增量规格组织迭代 | 暂缓；以后多个并发变更反复出现规格同步问题时优先评估 |

以上工具能力据 [Spec Kit 官方仓库](https://github.com/github/spec-kit)及 [SDD 说明](https://github.com/github/spec-kit/blob/main/spec-driven.md)、[OpenSpec 官方概念文档](https://github.com/Fission-AI/OpenSpec/blob/main/docs/concepts.md)。暂缓是本项目的成本判断，不是认为这些工具必须采用瀑布流程或不支持定制。

若后续采纳工具，先明确它如何消费/迁移 `docs/cleanroom`，保留一个权威契约集合；不能让自动生成目录与这里并行表达同一规则。需要模型检查时，优先对物化提交/恢复状态机做局部模型；当前不引入形式化建模工具。

## 每个切片使用同一条短流程

1. **定义行为**：更新所属规格的输入、输出、失败和场景；与已有契约冲突时写清替代行为及迁移影响。
2. **选择实现**：给出最小方案、实际依赖和检查入口。涉及不可逆数据变更或外部授权时，在相应动作前处理。
3. **先建立可判定样本**：纯逻辑用内存夹具；文件与恢复用临时工作区；真实设备和账号放入单独显式入口。
4. **实现并验证**：修复失败路径和相邻调用者，测试通过后对照原契约，不通过削弱断言制造完成。
5. **交付同一候选**：记录场景编号、测试位置/命令、实际结果及剩余限制。只在证据对应当前候选时标记完成。

不改变行为的小修复直接补针对性回归，不要求新增 PRD、ADR、设计文档和任务目录。改变核心边界、数据语义或重要依赖时，在相关规格追加简短决定理由；只有需要独立长期追踪的决定才拆单独 ADR。

## 文档状态与权威

- 入口区分用户已确认方向和设计提案。v0.1 是规格基线；具体功能状态由实现与验收证据说明。
- `architecture.md` 管边界；`layerfs.md` 管文件语义；`runtime.md` 管游戏运行语义；`acceptance.md` 只管覆盖与实施顺序。
- 事实证据放 `legacy-evidence.md`；它不能覆盖新规格的明确决定。
- 验收编号稳定保留。改变场景含义时写明原因；删除场景要检查依赖，不能为了实现方便移除要求。
- 有效的小范围设计可以进入对应实现，不要求对每个字段再确认。产品范围、数据兼容语义、外部权限和重大成本的变化由项目负责人决定。

## 协作分工

项目负责人负责方向、冲突取舍和最终验收。GPT-6.1 Sol 可承担契约设计、实现方案和独立评审；GPT-6 Luna 适合清单、引用、格式、重复性迁移与机械检查。每个契约或状态机保持一个活跃写入负责人，评审发现返回原负责人修订。

实施任务至少附带：目标、写区、相关契约和场景编号、实际输入、不可改边界、验收证据与停止条件。不能只分配一个文件名，也不把任务完成消息当作验收结果。

## 文件系统第一轮交付条件

- 规格留在 `docs/cleanroom`；实现使用 `cleanroom` 下独立的 Java 25 构建，旧入口继续保留。
- FS-01～FS-04、FS-14 具备真实解析实现、自动测试和来源解释示例。
- 文档记录已验证的范围；磁盘隔离、共享可写、升级恢复及游戏启动不能提前标记完成。
- 公开候选不含开发者目录、账户凭据、私有实例和本机构建报告；运行[分享检查](sharing.md)。
- 当前不安装规格框架；Git 提交、推送与发布按维护者明确授权的范围执行。

## 第二轮以用户故事验收

玩家共享预设和基础包使用同一种实例修订。先让该预设派生 A、B，私有复制真实文件；在 A 中修改配置、增加文件、删除文件，再重新打开并准备 A。验收结果是 A 的变化全部保留，B 与原内容不变。预设本身也走相同的准备入口，未提升的 delta 不成为后代继承输入。

本轮不做链接优化、升级合并、共享可写或游戏启动。核心拥有基线/delta 规则，宿主拥有复制、扫描、名称限制和持久化。失败与不完整状态必须保留数据并拒绝假就绪；完整崩溃恢复仍按后续场景验证。

规格与可执行示例一起交付，先按上述故事验收，再按维护者授权处理提交与分享。
