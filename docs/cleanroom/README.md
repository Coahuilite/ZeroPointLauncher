# ZeroPointLauncher 重构规格

规格版本：v0.1 · 日期：2026-10-21 · 当前切片：文件系统纯内核。

目标是把原作者的实例继承、共享和差异管理理念发展成通用 Minecraft 实例管理能力。首个完整场景采用 GTNH，同时支持普通实例与用户自建内容，不将 GTNH 写进文件系统或运行时核心。

## 用户已确认的方向

- 允许重新实现整个项目，保留原作者的设计理念，不受旧类和 API 结构约束。
- 核心与前端解耦，核心与宿主适配解耦；平台差异作为数据和能力输入。
- 启动器采用 Java 25，游戏 JVM 独立选择并支持多个版本共存。
- 前端采用 Qz-UILib-Core 和 Qz-UILib-Platform 路线。
- GTNH-first，not only GTNH；整合包导入和用户自建实例使用同一管理模型。
- 新重构规格放在 `docs`；当前进入文件系统第一轮实现，准备供其他开发者阅读和运行的源码，不执行远端推送。

本目录的 cleanroom 指按行为规格重新实现的工程路线。旧源码已经被阅读并记录在证据索引中。原作者署名和现有许可文件保留，迁移兼容性由可观察行为决定。

## 本版提出的设计选择

- 模块化单体；界面和核心在一个启动器进程中，游戏单独运行，特权助手仅按实际需要设置。
- 单父实例继承、不可变修订、显式共享组；不开发操作系统文件系统驱动。
- 逻辑文件树解析与实际磁盘执行分离，可写内容默认使用实例私有副本。
- 核心支持跨平台规划；初始真实桌面和文件操作验收先覆盖 Windows，其他平台经适配和真实验证后声明支持。
- 采用仓内 Markdown、稳定场景编号与版本控制组成的轻量规格驱动流程，暂不安装 Spec Kit 或 OpenSpec。

这些是本版建议的实施基线，不代表已经完成实现或取得跨平台兼容性证据。后续修订直接更新所属章节，并在有行为变化时补充迁移影响。

## 首个产品闭环

导入一个明确版本的 GTNH 实例，创建个人子实例，覆盖配置并添加本地模组，在 Qz 界面查看文件来源，准备运行目录并启动游戏。修改子实例配置不改变父层；退出和失败可观察；重复准备不丢失个人修改。

普通 Minecraft 组件样本和自建实例样本从内核测试开始参与，防止核心依赖 GTNH 名称、目录惯例或固定 Java 模板。

## 范围与实施前待定项

初版规格覆盖管理模型、核心端口、运行时解析、操作生命周期和验证策略。首个闭环不要求同时支持全部加载器、全部整合包格式、模组商店、云同步、插件市场或启动器自动更新。

| 待定项 | 影响的工作 | 负责人及完成条件 |
| --- | --- | --- |
| 首个 GTNH 实包版本及对应组件修订 | 真实启动验收，不阻挡纯内核测试 | 运行时实现负责人在 E2E 开始前固定包、来源、组件及 Java 组合 |
| 持久化格式与迁移提交协议 | 写入真实实例 | 文件系统实现负责人先以临时目录验证 schema 版本、失败恢复和旧数据导入，再开放真实数据写入 |
| Qz 配套版本及 Java 25 桌面行为 | 桌面适配 | 前端负责人固定配套产物，完成中文输入、缩放、异步任务及打包冒烟场景 |
| 微软认证应用身份与服务可用性 | 正式账户真实登录 | 认证负责人核实本项目可使用的注册身份；真实账号验证由账户所有者参与，不沿用未确认控制权的旧应用身份 |
| Linux/macOS 发行范围与宿主实现 | 对应平台正式发行 | 平台负责人完成相同契约的本机验收；不将 Windows 结果外推 |

以上是对应实施阶段的输入，不是纯内核开发的前置条件。各场景的实现与验证状态见[验收记录](acceptance.md)，不能从规格存在推断功能已经可用。
