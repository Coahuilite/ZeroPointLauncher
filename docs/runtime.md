# Minecraft 运行时合同 v0.1

## 1. 方向、范围与规范状态

- **已确认方向**：平台无关核心；前端、宿主分别解耦；启动器使用 Java 25，游戏使用独立选择的 JVM。
- **已确认方向**：GTNH-first，非 GTNH-only；保留普通实例与本地 JAR 的可用路径。
- **本轮提案**：本文的概念字段、约束判定、状态和验收场景，供初版实现与相邻规范采用。
- 本文定义行为合同，不固定 Java 类名、方法签名、下载服务商、认证库或进程库。
- 首个端到端对象是明确版本的 GTNH 实例；普适样本是使用合适 loader 的普通非 GTNH 实例及本地 JAR 模组。
- 支持矩阵必须逐项声明已验证的 Minecraft、loader、pack、OS 与架构组合，不承诺全生态兼容。

## 2. 三种架构与两个 Java 角色

| 概念 | 含义 | 不得据此推断 |
| --- | --- | --- |
| DeviceEnvironment | 设备的 OS、硬件架构及已知的进程执行能力 | 硬件架构就是宿主或游戏进程架构 |
| LauncherRuntime | 承载启动器宿主的 Java 25 进程及其架构 | 游戏也应使用 Java 25 或同一可执行文件 |
| GameRuntime | 选定 Java 可执行文件的真实版本、进程架构及运行能力 | 版本足够新就兼容所有游戏配置 |
| TargetEnvironment | 本次游戏计划的 OS、进程架构、选定游戏 JVM 及相关条件 | 可以从当前 JVM 的系统属性隐式补全 |

- 启动器宿主主版本固定为 Java 25；补丁更新和发行版策略另行确定，不据此自动扩大到未来主版本。
- 游戏 JVM 可以是 8、17、21、25 或其他受支持版本；允许哪些版本由本次配置的约束决定。
- 宿主引导程序不满足 Java 25 基线时，应在加载启动器主体前报告或进入明确的宿主恢复流程。
- 该流程不得修改游戏 JVM 选择；游戏 JVM 的配置不得改变宿主使用的 Java。
- 设备为 ARM64、宿主为 ARM64、游戏为 x86_64 是三个独立事实。
- 跨架构执行是否可用由宿主提供证据，例如已知执行能力或受控探测；核心不猜测模拟/转译能力。
- 探测结果保留真实主版本、更新版本、发行版原始信息与架构，不把所有“17 以上”折叠为一个类别。
- 无法识别或无法执行的 Java 是明确的探测结果，不伪装成不兼容版本或可用候选。

## 3. 显式环境输入

核心解析与规划必须接收 `TargetEnvironment`；不得在规划过程中读取当前 OS、当前 JVM 架构或 PATH。

```text
TargetEnvironment:
  osFamily: windows | linux | macos | ...
  osVersion: 已知值或 unknown
  gameProcessArchitecture: x86_64 | aarch64 | ...
  gameRuntime: 实际选定的游戏 JVM 描述
  nativeAbi: 已知值、not-applicable 或 unknown
  features: 本次规则判定需要的显式能力集合
```

- 仅在输入元数据确实使用某项条件时，才要求提供相应环境事实。
- 规则依赖 OS 版本、ABI 或能力但该值未知时，返回未决条件，不默认匹配也不默认排除。
- 候选游戏 JVM 架构必须与目标游戏进程架构一致；设备还必须能够执行该进程。
- 交叉规划可以针对与宿主不同的目标环境；“能生成计划”不表示当前设备能执行。
- 宿主执行前重新确认目标、选定 JVM 与设备能力，环境变化使旧计划失效时返回具体原因。

## 4. 游戏 JVM 兼容性是约束交集

输入约束来自已知的 Minecraft 版本、loader、pack 配置及明确的环境限制，并保留来源和适用范围。
每条约束可表达版本集合、闭/开区间、排除项、架构或必要能力，不能只表达最低主版本。

```text
有效候选 = Minecraft 约束 ∩ loader 约束 ∩ pack 约束 ∩ 目标环境约束
```

- 区分硬性要求、已知不兼容和推荐配置；推荐偏好不自动升级为硬性限制。
- 声明冲突导致交集为空时，报告冲突来源与条件，不以“选最新 Java”掩盖冲突。
- 有约束缺失时，仍使用已有约束判定；“未声明”不等于“支持任意版本”。
- 判定结果同时返回已知要求的满足/不满足情况与未知条件列表；已知冲突不能被未知项覆盖。
- “已知要求满足”只说明所收集要求成立；来源覆盖情况随结果返回，不显示为全面兼容证明。
- 不要求所有普通实例、本地 JAR 或旧整合包先补齐元数据，才允许进入已有的启动流程。
- 对不存在已知冲突但有未知条件的可执行配置，提供继续尝试路径，显示未知条件并记录本次选择。
- 必要执行事实缺失，例如找不到 Java 或无法确定待用 native，必须阻止执行并指出缺失事实。
- 不为猜测的 loader/pack 要求创建硬性阻断；实际失败证据可形成带适用范围的新诊断或规则。

### 4.1 显式选择与自动选择

- 用户指定可执行文件时，先探测该文件，再验证约束；不得静默改用其他 Java。
- 显式选择违反已知硬性要求时，返回不满足项与可选修正，不生成可执行启动计划。
- 显式选择存在未知条件时，按上述继续尝试规则处理，不自动把它替换成“更保险”的候选。
- 自动选择是用户可见的独立模式：在满足已知要求的候选中选择，并返回选择依据及未知条件。
- 自动选择不隐含自动下载、安装或改写已有配置；这些动作需要独立的产品策略与授权。
- pack 的 Java 推荐可影响自动模式排序，但不能覆盖显式选择或其他来源的硬性约束。

## 5. 解析、准备与启动计划

规划输入来自应用层提供的有效实例配置、对应文件修订及环境事实；配置继承合同以 [architecture.md](architecture.md) 为准。
有效配置已按固定父修订求得游戏组件组与可移植启动偏好组：子级未声明则继承，显式声明整组替换，参数列表也不例外。
Minecraft 核心再按游戏版本/loader 自身的元数据规则解析组件；这与实例级配置继承不同，均不使用任意 JSON 深合并。
父修订切换后，规划只接受配置与文件基线一致的修订快照，重新求 Java/平台约束，并报告保留子级覆盖的影响。
账户、秘密和实际 Java 路径不从父实例继承；执行时使用本次授权账户及本机选择的游戏 JVM。
核心据此产生纯数据计划；应用层协调宿主与外部服务适配器执行。
规划不下载文件、不获取 token、不创建链接、不启动 Java，也不通过 UI 对象回调改变状态。

`LaunchPlan` 的概念输出包括：

- 本次实例及配置快照标识、目标环境、选定游戏 JVM 的探测描述与选择来源。
- 游戏主类、已分词 JVM 参数和游戏参数模板；不依赖 shell 再次拆分参数。
- 有序 classpath、native 选择及准备要求、逻辑工作目录和显式环境变量要求。
- 所需游戏文件与本地 JAR 引用、已知校验信息及可用来源描述；不绑定特定下载商。
- 逻辑工作区标识及期望修订、约束判定结果、未决条件、启动阶段与可用就绪判据。
- 账户公开标识及所需会话字段名称；参数模板只包含待绑定符号，不包含秘密值。

`PLANNED` 不要求工作区已经物化；计划只引用逻辑工作区及期望修订，不持有未来的准备结果。
`PREPARING` 完成后，应用层将实际 ready 工作区及修订绑定为执行请求，并确认它满足原计划。
绑定时发现修订冲突则重新规划或报告冲突，不把旧计划静默用于新工作区。

计划不得包含 access token、refresh token、设备登录码或可兑换秘密的授权能力句柄。
账户公开标识仅用于查找已授权账户，不得单独授予取得凭据的权限。
应用层通过认证适配器取得授权会话；受控执行边界将秘密绑定到参数并直接交给进程启动器，不回写计划。
日志只记录允许公开的计划摘要；不得记录绑定后的完整命令、秘密环境变量或认证请求体。
本地路径和账户名称的日志展示遵循宿主隐私策略，不因计划无 token 就默认全部输出。

### 5.1 游戏规则、宿主与外部服务的分界

- Minecraft 核心负责版本参数语义、规则条件、classpath 顺序、native classifier 和排除规则。
- 宿主适配器负责路径表示与解析、文件读写、磁盘解压、权限、进程创建及平台能力探测。
- 外部服务适配器负责网络传输、制品/元数据源及远程认证；应用层协调获取结果与本地落盘。
- classpath 的逻辑条目由核心决定；宿主按目标平台编码路径列表，不硬编码 Windows 分号。
- native 文件选择基于目标游戏环境，不基于 UI/宿主 JVM 的架构或图形后端。
- native 准备必须在进程启动前完成，并返回实际结果；提交后台解压不等于完成。
- 路径不存在、文件不匹配或准备失败时，返回对应文件/阶段的错误，不继续报告准备成功。
- 文件系统层提供已准备的运行目录及结果证据；运行时不得自行另造一套层叠/共享规则。
- 普通本地 JAR 不因缺少仓库 ID 或远程地址而被拒绝；仍受实际路径和可读性检查约束。
- Qz/UI 所用 LWJGL、native 与图形依赖只属于前端宿主；不得注入游戏 classpath 或 native 目录。
- 游戏自身使用的 LWJGL 或 lwjgl3ify 由游戏配置解析，与 UI 选型分别管理。

## 6. 进程生命周期与取消

应用层将绑定 ready 工作区的执行请求交给进程宿主，取得可观察的游戏会话，而非只有字符串进度或布尔值。
建议生命周期如下；具体事件 API 留待实现设计：

```text
PLANNED → PREPARING → READY_TO_START → PROCESS_STARTED → EXITED
               ↘ FAILED              ↘ FAILED
               ↘ CANCELLED
PROCESS_STARTED 后可另发 GAME_READY；并非所有配置都有可靠就绪检测器。
```

- `READY_TO_START`：文件与 native、实际 ready 工作区绑定、JVM 校验和所需会话授权均已准备完成。
- `PROCESS_STARTED`：操作系统成功创建游戏进程；这只是进程启动成功，不代表游戏已可玩。
- `GAME_READY`：满足该游戏配置已声明且有依据的就绪判据，事件携带判据和观测证据。
- 没有可靠判据时显示“进程运行中，就绪未知”；不凭延迟、单条通用 LWJGL 日志推断所有游戏就绪。
- 进程在就绪前退出，应记录退出事实与阶段；有失败证据则报告失败，否则保留原因未知。
- 退出记录包含退出码或不可获取原因、时间与是否由用户停止；非零退出不等同于已诊断根因。
- 进程启动失败直接结束启动操作；输出流结束、子进程退出都不得留下无限等待的启动任务。
- stdout/stderr 消费与退出观测分别管理；结束后释放流与观察资源，不依赖 UI 持续存在。
- 准备阶段取消一旦被接受，必须保证不再创建游戏进程，并取消本操作拥有的未完成工作。
- 取消不删除其他实例共享资源；部分下载、目录准备的保留/回收由各资源所有者返回结果。
- 在进程创建临界点取消，执行器必须明确返回“取消已接受且未创建”或“已创建并返回会话”。
- 进程已创建后，关闭进度面板或取消观察不自动杀死游戏；停止游戏是独立的显式请求。
- 停止操作报告请求、等待和实际退出结果；未确认退出时不得显示“已停止”。
- 关闭窗口不终止游戏；应用退出的交互方式可以待定，但必须维持或可恢复会话占用保护。

### 6.1 会话占用与崩溃恢复

- 进程创建前持久化启动意图及实例、共享可写组的占用；创建后将占用交接给运行会话。
- 会话持久记录进程身份与占用资源；身份至少可区分 PID 重用，具体平台识别机制由宿主实现。
- UI 关闭、取消观察、启动器退出或崩溃都不是释放依据；不得据此允许冲突的准备、升级或启动。
- 恢复时核实原进程存活或已退出；确认退出/未创建后才释放占用，仍存活则恢复保护与观察。
- 进程身份或创建交接无法核实时，显示“占用待解决”并阻止冲突操作，不假定进程已经结束。
- 应用层与宿主负责人必须在首次真实启动前确定并验证持久记录、交接及恢复机制。

## 7. 账户与秘密存储边界

- 应用层拥有认证使用流程，认证服务适配器完成远程登录/刷新；Minecraft 规则解析不负责交互式登录。
- 前端只展示账户摘要、授权挑战和状态，不持有 refresh token 或完整的已绑定启动命令。
- 首次授权成功前不把账户标记为可用；取消、过期、无所有权或网络失败有独立结果。
- 秘密存储通过宿主能力提供，普通实例配置、pack 导出与日志不得包含账户秘密。
- 平台没有合适秘密存储时，应明确选择临时会话或另行批准的策略，不静默写入普通配置文件。
- 游戏执行需要的短期凭据仅在执行边界短时存在；诊断、异常和进程输出进入日志前需脱敏。
- 离线账户与在线账户走相同的公开账户/会话合同；在线失败不得静默切换为离线身份。
- 账户服务若无法提供所需会话，启动在创建进程前结束并返回可行动原因。

## 8. 输入输出示例

以下版本条件是合同示例，不是对实际 GTNH 或 loader 的版本要求声明。

```text
输入 A：宿主 Java 25；目标 windows/x86_64；用户指定 Java 8；
        已知游戏约束为 Java 8，设备可执行该 JVM。
输出 A：满足已知要求；计划仍使用 Java 8，宿主继续使用 Java 25。

输入 B：游戏要求 >=17；loader 要求 [17,21]；pack 要求 {21}；
        用户指定 Java 25。
输出 B：不满足 loader/pack 约束；不创建进程，不静默改用已安装的 Java 21。

输入 C：普通非 GTNH 实例 + 合适 loader + 可读本地 JAR；pack 未声明 Java 约束；
        已知游戏约束满足，其余执行事实齐备。
输出 C：返回已知要求满足及 pack 约束未知；允许明确继续，不要求补齐全包元数据。

输入 D：设备 ARM64、宿主 ARM64、目标游戏 x86_64；
        游戏 JVM 为 x86_64，但设备的跨架构执行能力未知。
输出 D：可返回目标解析计划；执行前要求宿主确认能力，不从宿主架构直接断言可执行。
```

## 9. 验收场景

- **RT-01 宿主与游戏分离**：Java 25 宿主使用满足配置要求的 Java 8 游戏 JVM，互不覆盖配置。
- **RT-02 约束交集**：复现示例 B；包含上界/集合的要求生效，并列出冲突来源。
- **RT-03 显式选择不替换**：指定 JVM 不满足硬性要求时失败，其他已安装 JVM 不被偷偷使用。
- **RT-04 未知不伪装兼容**：复现示例 C；展示未知并可继续，本地 JAR 不需要远程仓库元数据。
- **RT-05 环境显式与架构区分**：同一配置分别输入不同目标，native 随目标变化；复现示例 D。
- **RT-06 纯计划与秘密边界**：无需已有工作区即可纯规划；准备后按期望修订绑定 ready 工作区；计划、日志、导出均不含测试秘密哨兵值。
- **RT-07 游戏依赖隔离**：切换前端图形依赖不改变游戏 classpath/native；游戏规则仍正确求值。
- **RT-08 准备完整性**：native 解压失败或运行目录准备失败时不创建进程，失败阶段与文件可定位。
- **RT-09 启动与就绪分离**：进程创建、已知就绪、就绪未知、早退及启动失败分别产生正确结果。
- **RT-10 取消竞争与停止**：覆盖准备取消及创建临界点；已创建会话可追踪，关闭面板不杀游戏。
- **RT-11 认证失败与存储**：授权取消/过期不产生可用账户；在线失败不离线回退，不明文落盘。
- **RT-12 首个端到端**：选定并记录 GTNH 版本/loader/JVM/目标环境，完成准备、启动、观测与退出。
- **RT-13 普适端到端**：合适 loader 下的普通非 GTNH 实例 + 本地 JAR 完成同一生命周期，以游戏侧模组清单、日志或可观察行为确认模组确被加载；仅向原版 mods 目录放入 JAR 并启动不算通过，不依赖 GTNH 目录名或映射表。
- **RT-14 占用持久化与恢复**：游戏存活时关闭 UI/退出或崩溃后重开，实例与共享可写组仍受保护；身份无法核实则占用待解决，确认退出才释放。
- **RT-15 配置继承与父修订升级**：可启动父配置派生仅添加本地 JAR 的子实例，沿用有效组件/偏好，准备输入包含子层所选 JAR；实际加载由 RT-13 验证；升级父修订时配置/文件基线共同预览与提交、修订一致、重验 Java/平台约束并显示保留子级覆盖的影响，无账户、秘密或实际 Java 路径继承。

## 10. 相邻接口与未决项
